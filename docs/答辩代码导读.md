## 先记住这条主线

```text
kv-client main
  → client::run / run_with_io
  → protocol::parse_command / encode_request_line
  → TCP
  → server::serve / handle_connection
  → protocol::read_frame / parse_request_bytes
  → server::dispatch
  → Arc<Mutex<PersistentStore>>
  → PersistentStore（先写 WAL）
  → Store（BTreeMap）
  → Response
  → TCP
  → client::display_response
```

一句话概括：**客户端负责把人类命令变成 JSON Lines；服务器负责连接和分发；`PersistentStore` 在同一把锁内保证“WAL 成功后才改内存”；`Store` 用 `BTreeMap` 保存最终内存状态。**

## 3. 真实请求调用链

### 3.1 `set course rust` 的完整实际链路

客户端连接是在进入交互循环前建立的：`src/client.rs:131` 的 `TcpStream::connect` 对应服务端 `src/server.rs:167` 的 `accept`；服务端随后在 `src/server.rs:173` 为该连接创建线程。以下从用户输入开始追踪。

| 步骤 | 文件 / 函数 | 输入 | 输出 |
| ---: | --- | --- | --- |
| 1 | `src/client.rs:166`，`run_with_io` | 标准输入的一行 `set course rust\n` | `String line` 拥有该行文本 |
| 2 | `src/client.rs:189` → `src/protocol.rs:239`，`parse_command(&line)` | 借用 `&str` | 调 `tokenize`，得到 `Vec<String>`：`["set", "course", "rust"]` |
| 3 | `src/protocol.rs:545`，`tokenize` | `set course rust` 的字节视图 | 三个拥有所有权的 token；普通参数按 ASCII 空白分隔，带引号参数按 JSON 字符串解析 |
| 4 | `src/protocol.rs:248-285`，`parse_command` | token 向量 | `Request::Set { key: "course".to_owned(), value: "rust".to_owned() }`；随后 `Request::validate` 检查键值 |
| 5 | `src/client.rs:198-200` → `src/protocol.rs:220`，`encode_request_line` | `&Request` | `Vec<u8>`，内容为 `{"cmd":"set","key":"course","value":"rust"}\n` |
| 6 | `src/client.rs:140-143,208`，发送闭包 | `&encoded`，即 `&[u8]` | `TcpStream::write_all` 后 `flush`；字节进入 TCP 字节流 |
| 7 | `src/server.rs:193` → `src/protocol.rs:29`，`read_frame` | `BufReader<TcpStream>` 中可能分多次到达的字节 | `Frame::Line(Vec<u8>)`，包含结尾 LF；粘在后面的下一帧仍留在缓冲区 |
| 8 | `src/server.rs:207` → `src/protocol.rs:186`，`parse_request_bytes` | 一帧原始字节 | UTF-8 合法时得到 `&str`；非法时得到 `AppError::Protocol(INVALID_UTF8)` |
| 9 | `src/protocol.rs:163`，`parse_request_line` | 完整 JSON Lines 文本 | 去 LF/可选 CR、检查 64 KiB、JSON 解码为 `Value`、检查字段、反序列化并再次业务校验，最终输出 `Request::Set` |
| 10 | `src/server.rs:208,222`，`dispatch` | `Request::Set` 被按值移动进入分发 | match 解构出拥有所有权的 `String key/value` |
| 11 | `src/server.rs:227-230`，`dispatch` 的 Set 分支 | `&Arc<Mutex<PersistentStore>>` | `lock()` 得到可变 `MutexGuard`；调用 `PersistentStore::set(&key, &value)` |
| 12 | `src/persistence.rs:58`，`PersistentStore::set` | 借用的 `"course"`、`"rust"` | 检查 `writable`、键值合法性，并读取当前是否存在，得到 `replaced` |
| 13 | `src/persistence.rs:63-66`，构造 `WalRecord::Set` | 借用的键和值 | 新建拥有自身 `String` 的临时 WAL 记录 |
| 14 | `src/persistence.rs:115`，`append_record` | `&WalRecord::Set` | JSON 编码后追加 LF，形成 `{"op":"set","key":"course","value":"rust"}\n` |
| 15 | `src/persistence.rs:128-130`，`append_record` | WAL 字节 | 顺序执行 `write_all` → `flush` → `sync_data`；全部成功才返回 `Ok(())` |
| 16 | `src/persistence.rs:67` → `src/storage.rs:38`，`Store::set` | 同一锁内借用的键和值 | `BTreeMap::insert` 获取自己的字符串副本；首次插入输出 `SetOutcome { replaced: false }` |
| 17 | `src/server.rs:231-239`，`dispatch` | `SetOutcome` | MutexGuard 在闭包返回时释放；随后构造 `Response::success(ResponseData::Set { replaced: false })` |
| 18 | `src/server.rs:289`，`write_response` | `&Response` | `{"ok":true,"data":{"kind":"set","replaced":false}}\n`，经 `write_all` 和 `flush` 回到 TCP |
| 19 | `src/client.rs:145,213-237`，接收与解析 | 服务端响应字节 | `read_frame` → UTF-8 → `parse_response_line` → `Response` |
| 20 | `src/client.rs:239,250-282`，`display_response` | `&Response` | 首次写入显示 `created`；若原键已存在则显示 `replaced`，然后打印下一次提示符 |

关键状态变化只有这一段，并且全在同一把 Mutex 锁内：

```text
WAL write_all → flush → sync_data → BTreeMap::insert
```

只要前三步任一步报错，`?` 就会阻止 `BTreeMap::insert` 执行，服务端返回 `STORAGE_ERROR` 而不是成功。

### 3.2 `get course` 简要实际链路

```text
"get course\n"
→ parse_command
→ Request::Get { key: "course" }
→ {"cmd":"get","key":"course"}\n
→ TCP / read_frame / parse_request_bytes
→ dispatch(Request::Get)
→ Mutex::lock
→ PersistentStore::get
→ Store::get
→ BTreeMap::get("course").cloned()
→ 释放 MutexGuard
→ ResponseData::Get { value: "rust" }
→ {"ok":true,"data":{"kind":"get","value":"rust"}}\n
→ 客户端显示：value: rust
```

`get` **不写 WAL**。`Store::get` 在锁内把 `String` 克隆出来；因此锁释放后，响应仍拥有独立的值，可以安全编码和发送。

### 3.3 `delete course` 简要实际链路

```text
"delete course\n"
→ parse_command
→ Request::Delete { key: "course" }
→ {"cmd":"delete","key":"course"}\n
→ TCP / read_frame / parse_request_bytes
→ dispatch(Request::Delete)
→ Mutex::lock
→ PersistentStore::delete
   → ensure_writable
   → validate_key
   → contains_key（不存在则立即 NOT_FOUND，且不写 WAL）
   → append {"op":"delete","key":"course"}\n
   → flush
   → sync_data
   → Store::delete / BTreeMap::remove
→ 释放 MutexGuard
→ ResponseData::Delete { deleted: true }
→ 客户端显示：deleted: true
```

删除后再次 `get course` 或 `delete course`，最终由 `Store` / `PersistentStore` 返回 `AppError::NotFound`，服务端编码成 `NOT_FOUND`。

## 5. 所有权与并发热点

### 热点 1：文本输入先拥有，再借用解析

`src/client.rs:181-190`

```rust
let mut line = String::new();
input.read_line(&mut line)?;
let request = parse_command(&line)?;
```

`line` 拥有输入字符；`read_line` 通过 `&mut String` 修改它，`parse_command` 只借用 `&line`。解析结束后借用终止，下一轮可以 `line.clear()` 并复用分配的容量。

### 热点 2：token 的 `String` clone 是真实数据复制

`src/protocol.rs:248-252`

```rust
Request::Set {
    key: tokens[1].clone(),
    value: tokens[2].clone(),
}
```

这里 clone 的是两个 `String` 的堆数据，不是指针引用计数。原因是通过索引只能借用 `Vec` 元素，而返回的 `Request` 必须独立拥有键和值。

### 热点 3：请求按值进入 `dispatch`，match 移动字段

`src/server.rs:222-230`

```rust
fn dispatch(request: Request, store: &Arc<Mutex<PersistentStore>>) -> (Response, bool) {
    match request {
        Request::Set { key, value } => { /* ... */ }
```

`request` 的所有权从连接处理函数移动到 `dispatch`；match 再把 `key`、`value` 两个 `String` 移出枚举。调用 `store.set(&key, &value)` 时只是临时借用，分支结束后这两个局部值被释放。

### 热点 4：`Arc::clone` 只克隆共享指针，不复制 Store/WAL

`src/server.rs:167-173`

```rust
let shared_store = Arc::clone(&store);
thread::spawn(move || handle_connection(stream, shared_store));
```

`Arc::clone` 增加引用计数，所有线程仍指向同一个 `Mutex<PersistentStore>`；不会复制 `BTreeMap`，也不会打开第二个 WAL。`move` 把 `stream` 和这一个 Arc 句柄的所有权转移给新线程，使线程闭包满足所需生命周期。

### 热点 5：一条 TCP 连接拆成读句柄和写句柄

`src/server.rs:184-190`；客户端对应 `src/client.rs:131-135`

```rust
let writer = match stream.try_clone() {
    Ok(writer) => writer,
    Err(_) => return,
};
let mut reader = BufReader::new(stream);
```

原 `TcpStream` 被移动进 `BufReader`；`try_clone` 复制的是指向同一底层 socket 的系统句柄，不是复制网络数据。这样读侧可保持缓冲状态，写侧可独立调用 `write_all/flush`。

### 热点 6：锁在 `dispatch` 中获得，并在结果产生后立即释放

`src/server.rs:226-239`

```rust
let result = store
    .lock()
    .map_err(|_| AppError::Message("storage mutex poisoned".to_owned()))
    .and_then(|mut store| store.set(&key, &value));
```

`lock()` 成功后产生 `MutexGuard<PersistentStore>`；闭包参数 `mut store` 允许通过 DerefMut 调用 `&mut self` 的 `set`。守卫在 `and_then` 闭包返回时 drop，因此后面的 `Response::success` 构造和 `write_response` 都不持锁。

写请求的锁范围包含：

```text
contains_key → WAL encode/write/flush/sync_data → BTreeMap 修改
```

这保证 WAL 顺序和内存修改顺序一致。

### 热点 7：`get` 和 `keys` clone 数据快照后释放锁

`src/storage.rs:49-54,68-69`

```rust
self.entries.get(key).cloned()
self.entries.keys().cloned().collect()
```

这里 clone 的是值字符串或所有键字符串，属于数据复制。代价换来清晰的并发边界：响应不借用 `BTreeMap` 内部数据，所以锁释放后仍能序列化并发送。

### 热点 8：`Store::set` 通过 `&mut self` 独占修改，并让映射拥有数据

`src/storage.rs:38-45`

```rust
self.entries.insert(key.to_owned(), value.to_owned())
```

`&mut self` 保证调用期间没有其他借用者修改同一 `Store`；`to_owned` 将借用的 `&str` 复制为映射拥有的 `String`。即使请求局部变量随后析构，BTreeMap 中的数据仍有效。

### 热点 9：WAL 临时记录拥有 String，但 append 只借用记录

`src/persistence.rs:63-67,115-117`

```rust
self.append_record(&WalRecord::Set {
    key: key.to_owned(),
    value: value.to_owned(),
})?;
```

临时 `WalRecord` 需要自己的字符串以满足 Serde 序列化；`append_record` 接收 `&WalRecord`，不夺走它。序列化产生新的 `Vec<u8>`；写完后临时记录与字节缓冲自动释放。

### 5.1 为什么网络 read/write 时不持锁

真实顺序是：

```text
read_frame（无锁）
→ UTF-8/JSON/字段校验（无锁）
→ dispatch 中 lock
→ 只做必要存储操作
→ MutexGuard drop
→ Response JSON 编码（无锁）
→ TcpStream::write_all/flush（无锁）
```

网络等待时间不可预测。如果读网络时持锁，一个空闲客户端会阻止全部客户端访问；如果写网络时持锁，一个接收很慢的客户端会拖住所有存储操作。当前 `idle_client_does_not_hold_storage_lock` 测试专门验证空闲连接不会占住存储锁。

### 5.2 本项目中的几种 clone 不要混淆

| 写法 | clone 的对象 | 是否复制 KV 数据 |
| --- | --- | --- |
| `Arc::clone(&store)` | Arc 句柄和引用计数 | 否 |
| `tokens[i].clone()` | 一个 `String` 的字符数据 | 是 |
| `BTreeMap::get(...).cloned()` | value `String` | 是 |
| `entries.keys().cloned()` | 每个 key `String` | 是 |
| `TcpStream::try_clone()` | 同一 socket 的系统句柄 | 否，不复制已传输字节 |

## 6. 持久化真实实现

### 6.1 `set` 的实际顺序

入口为 `src/persistence.rs:58` 的 `PersistentStore::set`：

```text
ensure_writable
→ validate_key / validate_value
→ contains_key，保存 replaced
→ 构造 WalRecord::Set（复制 key/value）
→ append_record
   → serde_json::to_vec
   → push LF
   → File::write_all
   → File::flush
   → File::sync_data
→ Store::set
→ BTreeMap::insert
→ SetOutcome { replaced }
```

`PersistentStore` 和 WAL 句柄都在 Mutex 内，所以两个客户端不可能同时写同一个文件句柄。`Store::set` 会再次校验键值；当前实现中前面已经用同一组函数验证过，因此 WAL 成功后这次校验没有新的正常失败条件。

### 6.2 `delete` 的实际顺序

入口为 `src/persistence.rs:77`：

```text
ensure_writable
→ validate_key
→ contains_key
   ├─ false：返回 NOT_FOUND，不写 WAL
   └─ true：继续
→ 构造 WalRecord::Delete
→ append_record：write_all → flush → sync_data
→ Store::delete
→ BTreeMap::remove
```

提前检查存在性很重要：否则删除不存在的键也会进入 WAL，而恢复时 `Store::delete` 会把这种记录判为损坏。

### 6.3 写入错误路径

`append_record` 把三个 I/O 操作放在一个返回 `io::Result<()>` 的闭包中。任意一步失败时：

1. 立即跳过内层 `Store::set/delete`，所以本次内存状态不更新；
2. `self.writable = false`，把该 `PersistentStore` 标记为永久不可写；
3. 返回 `AppError::Persistence("WAL write failed: ...")`；
4. 服务端经 `ErrorCode::StorageError` 返回 `STORAGE_ERROR`；
5. 后续 `set/delete` 被 `ensure_writable` 拒绝，但 `get/keys/status` 仍可读。

永久拒绝后续写，是因为 `write_all/flush/sync_data` 失败时无法安全断定文件末尾是否已经部分变化；继续追加可能掩盖或扩大损坏。`src/persistence.rs` 内置测试 `injected_write_failure_preserves_memory_and_poison_writes` 锁定了这条行为。

### 6.4 启动恢复的实际顺序

`PersistentStore::open` 与 `recover_wal` 的链路：

```text
取得 Path
→ 如有父目录则 create_dir_all
→ File::open
   ├─ 已存在：只确认可打开
   ├─ NotFound：create_new 创建空文件
   └─ 其他错误：返回
→ 再次 File::open，交给 recover_wal
→ Store::new
→ BufReader<File>
→ 循环 read_frame
   ├─ Eof：恢复完成
   ├─ Incomplete：报“该行没有 LF”
   ├─ TooLarge：报该行超过 65536 字节
   └─ Line：去 LF/可选 CR，拒绝空行
→ serde_json::from_slice::<WalRecord>
→ match WalRecord
   ├─ Set：Store::set
   └─ Delete：validate_key + Store::delete
→ 任一错误包装为带 1-based 行号的 AppError::Persistence
→ 恢复成功后用 append(true).read(true) 打开唯一 WAL 句柄
```

`WalRecord` 使用 `#[serde(tag = "op", rename_all = "lowercase", deny_unknown_fields)]`，所以只接受 `set/delete`、固定字段和固定类型。恢复不会跳过坏行、不会截断尾部、不会覆盖原文件；错误直接阻止服务器进入监听状态。

### 6.5 当前实现没有做的事情

- 没有快照、WAL 压缩或定期重写；文件只追加。
- 没有容忍“最后一条半写记录”；缺 LF 直接判损坏。
- 没有文件级跨进程锁；并发安全来自单进程中的 `Mutex`。
- 没有后台异步刷盘；写请求在线程内同步等待 `sync_data`。
- 没有事务批次；每个 `set/delete` 各是一条 WAL 记录。

## 9. 答辩高风险点：15 个追问与标准答案

### 1. 为什么是 `Arc<Mutex<PersistentStore>>`，不是 `Mutex<PersistentStore>`？

`Mutex` 只解决互斥，不提供多个线程共同拥有对象的能力；把普通 `Mutex` 借用移入 `thread::spawn` 无法满足线程可能长期存在的生命周期。`Arc` 让每个连接线程拥有一个引用计数句柄，`Mutex` 再保证同一时刻只有一个线程进入共享状态。

### 2. 为什么 Mutex 包住整个 `PersistentStore`，而不是只包 `BTreeMap`？

一次写操作必须把 WAL 追加顺序和 BTreeMap 修改顺序绑定起来。如果只锁映射而 WAL 句柄在锁外，多线程可能交错写 WAL，或 WAL 顺序与内存提交顺序不一致；当前一个 Mutex 同时保护 Store、File 和 `writable` 状态。

### 3. 锁在哪里获得、什么时候释放，为什么网络读写不持锁？

锁只在 `server::dispatch` 各存储分支的 `store.lock()` 获得，MutexGuard 在 `.and_then/.map` 闭包返回时释放。`read_frame`、JSON 解析、Response 编码和 TCP 写入都在锁外，避免空闲或慢客户端阻塞其他连接。

### 4. `Arc::clone(&store)` 会不会复制整份 KV 数据？项目里哪些 clone 真会复制数据？

不会；它只复制 Arc 句柄并增加引用计数，所有线程仍看到同一个 `PersistentStore`。`tokens[i].clone()`、`BTreeMap::get(...).cloned()` 和 `keys().cloned()` 才会复制 `String` 数据；这样响应在释放锁后仍拥有所需内容。

### 5. 为什么每个连接一个线程？它有什么边界？

源码在每次 `accept` 后直接 `thread::spawn`，实现简单，每个阻塞 `TcpStream` 有独立执行流，连接错误也相互隔离。代价是线程数没有上限、JoinHandle 被丢弃、生产 `run` 没有优雅停止和等待连接线程的流程；这是课程项目的明确规模边界。

### 6. 服务端和客户端为什么都调用 `TcpStream::try_clone`？

`BufReader` 需要拥有一个流并保留读取缓冲，同时代码还要独立写响应/请求。`try_clone` 得到同一底层 socket 的第二个句柄，不是复制 TCP 内容；原句柄进入 `BufReader`，克隆句柄负责写。

### 7. TCP 没有消息边界，项目如何处理分段和粘包？

`read_frame<R: BufRead>` 用 `fill_buf/consume` 持续寻找 LF：一帧可跨多次接收，LF 后的字节留给下一次调用。它只保留至多约 64 KiB 的当前帧，超长且有 LF 时丢弃到该 LF，再返回 `Frame::TooLarge`，所以不会把粘包误当一条 JSON。

### 8. 为什么用 `BTreeMap`，不用 `HashMap`？

需求规定 `keys` 按字典序返回。`BTreeMap::keys()` 本身就是有序迭代，`Store::keys` 只需 clone 并 collect；若用 `HashMap`，每次 keys 都要额外排序，且迭代顺序不稳定。

### 9. 为什么 `PersistentStore` 和 `Store` 都校验键值，看起来重复？

`Store` 是独立公开的内存存储，必须保护自身不变量；`PersistentStore` 必须在写 WAL **之前**拒绝非法数据，防止把坏记录落盘。恢复又通过 `Store::set/delete` 复用同一规则，因此网络写入和 WAL 重放不会采用不同限制。

### 10. 为什么一定先写 WAL，再改 BTreeMap？中间崩溃会怎样？

如果先改内存再落盘，服务器可能已经返回成功或暂时可读，但重启后数据消失。当前在同一锁内先 `write_all/flush/sync_data`，再修改映射；若同步后、内存更新前进程崩溃，重启会从已落盘记录重放出来，而客户端当时也不会收到由后续代码生成的成功响应。

### 11. `flush` 和 `sync_data` 有什么区别，为什么两个都调用？

`flush` 完成 Rust 写入接口层面的刷新，`sync_data` 请求操作系统把文件数据同步到持久存储；只有 `flush` 不能表达项目要求的耐久边界。实际持久性仍受操作系统、文件系统和硬件保证约束，但代码已使用标准库提供的同步数据接口。

### 12. WAL 写到一半失败后，为什么把 `writable` 永久设为 false？

I/O 失败时可能已经产生部分尾记录，进程无法可靠判断文件当前位置是否仍安全。源码因此不更新内存，并让后续 set/delete 全部返回持久化错误；读操作仍可用，重启时严格恢复会检查 WAL 是否损坏。

### 13. 启动恢复为什么不忽略最后一条坏记录？

`recover_wal` 把缺 LF、空行、超长、坏 JSON、未知字段/操作和非法业务记录都视为损坏，并带行号返回错误。这样不会在用户不知情时丢掉一个“可能已确认”的写入，也不会自动覆盖取证所需的原文件；代价是人工处理损坏后才能启动。

### 14. 为什么既手工检查 JSON 字段，又让 Serde `deny_unknown_fields` 反序列化？`Result/?` 怎么参与？

手工 `validate_request_fields` 用于把缺字段、多字段和类型错误映射到项目规定的稳定错误码；Serde 再负责真正构造强类型枚举，并作为第二道结构检查。每一步返回 `Result`，`?` 在失败处立即退出；`From<io::Error/serde_json::Error>` 和 `AppError::code` 最终把内部错误统一变成协议响应。

### 15. 项目有 `Store::status` 和 `PersistentStore::status`，为什么服务端 `status` 实际调用 `len()`？

`server::dispatch` 的 `Request::Status` 分支在锁内直接 `.map(|store| store.len())`，再构造 `ResponseData::Status { count }`；所以网络真实路径没有调用两个 `status()` 方法。当前行为与文档相同，因为 `status()` 也只是包装 `len()`，但答辩追踪代码时应说清真实调用，而不是按函数名猜测。

### 10.3 自动化测试没有直接证明的内容

这些不是“实现一定有 bug”，而是答辩时不能把它们说成已有自动测试证据：

1. 恰好两个客户端同时操作的独立自动测试；
2. 多线程 WAL 文件内容逐字节无交错；
3. 多线程写同一个键时某个确定线程必然成为最终值；
4. 真实 `kv-client.exe` 与 `kv-server.exe` 子进程的完整 CRUD 自动化；
5. 服务端响应被刻意拆成多个 TCP 包时的客户端专项测试；
6. Linux 构建、测试与运行结果。

### 10.4 最终答辩口径
