# 架构设计

## 1. 模块职责

核心服务器按职责分层，答辩网页通过本地控制器接入：

```text
答辩网页 / 命令行客户端
    │ HTTP控制器转发 / 解析用户命令
    ▼
协议层
    │ JSON Lines 编解码、帧限制、错误分类
    ▼
网络服务层
    │ Sync每连接线程 / Async每连接Tokio任务
    ▼
持久化统一入口 PersistentStore
    │ 先写增量WAL，再更新内存；Snapshot/Compact
    ▼
内存存储 Store
       BTreeMap、set/get/delete/keys/status
```

- 客户端只负责命令行参数、交互命令解析、请求发送和响应显示，不直接访问数据文件。
- 协议层负责完整读取一帧、UTF-8/JSON 校验和请求响应结构，不负责修改数据。
- 网络服务层负责连接和线程，不把网络等待带入存储锁。
- 存储层提供独立的键值接口，内存测试不需要网络。
- `PersistentStore` 统一协调“WAL 落盘后更新内存”，外部模块不能绕过它修改正式 Store。

## 2. 请求数据流

1. 服务器监听 `127.0.0.1:7878`；Sync 模式为连接创建线程，Async 模式创建 Tokio 任务。
2. 每个连接循环读取一条 LF 结束的请求帧。
3. 协议层在不持有存储锁的情况下验证 UTF-8、JSON、命令、参数和长度。
4. 合法请求调用存储接口。
5. 读操作在锁内取得必要数据的快照，随后释放锁，再序列化和发送响应。
6. 写操作在一次存储临界区内完成 WAL 追加、刷新、同步和内存更新，释放锁后发送响应。
7. `quit` 发送成功响应后只关闭当前连接；其他错误返回错误响应并继续循环。

## 3. 并发与锁范围

共享对象按启动参数选择 `Arc<Mutex<PersistentStore>>` 或 `Arc<RwLock<PersistentStore>>`。`PersistentStore` 同时持有 `BTreeMap`、唯一 WAL 写入器和 Snapshot 路径；每个连接只克隆 `Arc`，不复制数据。

锁的规则固定如下：

- 等待客户端输入、解析输入、构造网络响应和发送响应时不持锁。
- Mutex 模式下所有存储操作互斥；RwLock 模式下 `get/keys/status/storage_status` 使用共享读锁。
- `set`、`delete` 在独占锁内按“分配 seq → 计算 CRC32 → append → flush → sync_data → 更新 BTreeMap”执行。
- `compact` 使用独占锁，避免 Snapshot 与并发写入得到不一致状态。
- Async 模式通过 `spawn_blocking` 执行阻塞存储调用，避免 `sync_data` 长时间占用 Tokio I/O 工作线程。
- 任意持久化步骤失败时，内存不更新，也不返回成功。
- 所有写入通过同一个临界区串行化，因此 WAL 顺序与内存修改顺序一致。

## 4. 启动和关闭

启动时先校验并加载 `data/kv.snapshot`（若存在），再打开 `data/kv.wal`，验证版本、CRC32 和连续序号，只重放快照之后的增量记录；恢复失败则报告损坏/IO 错误并拒绝监听。正常关闭不依赖“退出时一次性保存”，因为每次成功修改已经同步到 WAL。

连接关闭、客户端异常和单条请求错误只终止当前连接循环。服务器监听线程不因单个客户端出错而停止。

## 5. 错误边界

可由客户端修正的请求错误通过协议返回固定错误码；不可恢复的启动持久化错误在服务器启动阶段报告。协议错误不得 panic。持久化 IO 错误不得伪装成成功；如果底层文件已发生不确定的部分写入，服务器至少必须拒绝后续成功写入并要求重新启动检查 WAL。

## 6. 平台边界

当前工作区已确认 Windows 上存在 Rust/Cargo 工具链。Linux 尚未实测；代码应使用标准 Rust/TCP 和平台无关路径处理，最终验收仍需在目标 Linux 环境执行构建、测试和演示。
