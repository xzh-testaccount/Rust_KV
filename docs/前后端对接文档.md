> - 文档状态：**决策落定版**（v0.2，2026-09-02；T-1 ~ T-12 已全部答复落定，见第 10 章决策记录）
> - 后端基线：TCP JSON Lines 协议，7 个固定命令（`set`/`get`/`delete`/`keys`/`status`/`ping`/`quit`）

## 1. 文档目标与适用范围

### 1.1 目标

1. 明确前端原型每个页面、每类交互所需的数据与后端能力；
2. 给出前后端之间的请求/响应格式、字段定义、错误码与状态约定；
3. 作为联调执行、问题定位和最终验收的共同依据。

### 1.2 适用范围

- 前端：`prototype/` 下的可视化实验平台（本地启动、本地访问，不部署）；
- 后端：`mvp/` 下的 Rust KV 服务器（默认 `127.0.0.1:7878`，数据文件 `data/kv.wal`）；
- 中间接入层：浏览器无法直接发起 TCP 连接，需要一个接入/代理层；**已定（T-1）**：方案 A，原型工程服务端代理，见第 2 章。

### 1.3 术语约定

| 术语       | 含义                                                     |
| -------- | ------------------------------------------------------ |
| 帧（frame） | 一条以 LF 结尾的 UTF-8 JSON 行，逻辑上限 64 KiB                    |
| 接入层      | 位于浏览器与 Rust 服务之间的代理（HTTP/WebSocket），见第 2 章             |
| 原型模拟     | 原型当前的纯前端本地模拟逻辑；按第 10 章决策，TTL 与指标类模拟删除，Compact/发布订阅保留模拟 |

## 2. 接入架构（联调前提）

### 2.1 现状与约束

- 后端协议是 **TCP + JSON Lines**（`protocol.rs` 中 `read_frame`/`parse_request_bytes`），一问一答，单连接可连续多帧。
- 浏览器环境**不能**直接建立裸 TCP 连接；原型页面注释也明确写着“所有交互均为本地原型模拟，不连接后端”。
- 因此必须有一个接入层把浏览器的调用翻译成 TCP JSON Lines。

### 2.2 接入方案（T-1 已定：方案 A）

| 方案           | 说明                                                                                                | 决策（T-1）                               |
| ------------ | ------------------------------------------------------------------------------------------------- | ------------------------------------- |
| A. 前端框架服务端代理 | 在 `prototype` 的服务端（vinext server action / API 路由）中用 Node `net` 模块连接 `127.0.0.1:7878`，对内暴露 HTTP 接口 | **✅ 采用（T-1 答复）**：改动集中在前端工程内，不改变后端设计意图 |
|              |                                                                                                   |                                       |
|              |                                                                                                   |                                       |

> 本文接口映射按方案 A 编写：前端页面调用接入层的 HTTP 端点，接入层与后端保持一条或多条 TCP 连接，逐帧转发。**该方案已确认（T-1），可以开工。**

### 2.3 连接与状态模型

- 前端以 `ping` 命令作为健康探测（后端返回 `{"ok":true,"data":{"kind":"ping"}}`）；
- `ServerState` 由前端根据探测结果与实验阶段推导：

| 前端状态         | 推导规则（T-6 / T-12 已定）                      |
| ------------ | ---------------------------------------- |
| `ONLINE`     | 最近一次 `ping` 成功                           |
| `OFFLINE`    | 连接失败/超时，或执行了“强制终止服务”                     |
| `STARTING`   | 进程刚拉起、端口尚未就绪（T-6 已定）                     |
| `RECOVERING` | 重启后进程存活但端口未就绪（WAL 重放中），统一显示“恢复中”（T-6 已定） |
| `ERROR`      | 连接成功但连续返回 `STORAGE_ERROR` 等不可恢复错误        |

## 3. 前端原型功能梳理与后端接口映射

### 3.1 页面入口与主要用户操作流程

原型为单页应用，入口结构：**顶栏**（品牌区 + 服务连接徽章 `127.0.0.1:7878` + “答辩模式”/“重置实验室”按钮）→ **六个标签页导航** → **全局指标条**（键总数、活跃客户端、实时吞吐、累计请求、成功率、WAL 大小）。各页面主流程：

| 页面   | 主操作流程                                                                                             |
| ---- | ------------------------------------------------------------------------------------------------- |
| 系统总览 | 纯展示：服务节点状态、实时吞吐曲线、WAL 健康状况、最近实验结论、最近请求流                                                           |
| 键值操作 | 填写键/值 → 执行 SET / GET / DELETE / KEYS → 结果卡片即时反馈；右侧存储视图同步更新；点击键卡片可把键值载入命令面板继续操作（TTL 输入框按 T-2 决策删除） |
| 并发实验 | 配置客户端数量（预设 1/10/50/100）、每客户端请求数、负载类型 → 开始实验 → 观察客户端活动矩阵、进度环、成功/失败数与实时吞吐 → 完成或手动停止                 |
| 崩溃恢复 | ① 选择写入键数（50/100/500/1000）并写入快照 → ② 强制终止服务 → ③ 重启并重放 WAL → 自动校验（数量、抽样值、数据指纹）；另可独立运行 WAL Compact    |
| 性能测试 | 勾选并发规模（可多选）与负载类型 → 运行基准测试 → 每完成一个规模追加一个数据点，驱动吞吐量柱状图与 P50/P95/P99 延迟折线图；可中途停止并保留已完成点               |
| 发布订阅 | 管理订阅者（添加至多 4 个、订阅/取消切换）→ 填写频道与消息 → 发布 → 观察消息投递动画、订阅者接收情况与事件日志                                     |

全局交互：`重置实验室` 通过 AlertDialog 二次确认后还原全部前端状态；服务离线时所有写操作与实验入口禁用，并引导用户到“崩溃恢复”页重启服务。

## 4. 接口与协议定义

### 4.1 传输层约定（现有后端，不变）

| 项    | 约定                                                                        |
| ---- | ------------------------------------------------------------------------- |
| 传输   | TCP，默认 `127.0.0.1:7878`（服务端可用 `--bind`/`--data` 覆盖）                       |
| 编码   | UTF-8 JSON Lines，每请求/响应一行，以 LF 结尾（接受 CRLF）                                |
| 帧上限  | 65,536 字节（不含结尾 LF）；超限请求回 `FRAME_TOO_LARGE`，超限响应同样回 `FRAME_TOO_LARGE`，不得截断 |
| 一问一答 | 每条请求恰好一条响应；单条请求错误不断开连接                                                    |
| 键约束  | 非空，不含空白字符/控制字符，UTF-8 ≤ 256 字节                                             |
| 值约束  | 非空，不含控制字符（允许空格），UTF-8 ≤ 16 KiB                                            |

### 4.2 接入层对浏览器暴露的 HTTP 接口（T-1 已定）

采用“单一命令代理端点”，接入层只负责把 JSON 请求转成一行发给后端并把响应行解析为 JSON 返回，不做业务改写：

```
POST /api/kv
Content-Type: application/json

{"cmd":"get","key":"course:name"}
```

响应即后端原始响应对象：

```json
{"ok":true,"data":{"kind":"get","value":"Rust 网络 KV 存储"}}
```

- 接入层网络/进程级故障时返回 HTTP 5xx 与统一错误体：

```json
{"ok":false,"error":{"code":"BACKEND_UNREACHABLE","message":"connect 127.0.0.1:7878 refused"}}
```

> `BACKEND_UNREACHABLE` 是**接入层新增码**，不在后端 11 个错误码之列；前端处理建议见第 6 章。**该端点形态已确认（T-1）。**

### 4.3 现有后端命令定义（已实现，联调直接可用）

#### 4.3.1 `set` — 写入（新增或覆盖）

请求：

```json
{"cmd":"set","key":"user:1001","value":"Alice"}
```

成功响应：

```json
{"ok":true,"data":{"kind":"set","replaced":false}}
```

| 字段         | 类型     | 说明            |
| ---------- | ------ | ------------- |
| `key`      | string | 必填；约束见 4.1    |
| `value`    | string | 必填；约束见 4.1    |
| `replaced` | bool   | 响应字段：是否覆盖了已有键 |

前端映射：键值操作页“写入 SET”。`replaced=true` 显示“已更新”，`false` 显示“已创建”。
**注意**：TTL **不支持**（T-2 已定）；前端需删除 TTL 输入框与 `expiresAt` 相关逻辑，`set` 请求只保留 `key`/`value` 字段，发送 `ttlSeconds` 等多余字段会触发 `EXTRA_ARGUMENT`。

#### 4.3.2 `get` — 读取

请求：`{"cmd":"get","key":"user:1001"}`
成功：`{"ok":true,"data":{"kind":"get","value":"Alice"}}`
失败（键不存在）：`{"ok":false,"error":{"code":"NOT_FOUND","message":"key \"user:1001\" does not exist"}}`

前端映射：GET 按钮；命中时把 `value` 回填到 Value 输入框；`NOT_FOUND` 显示“未找到”错误卡片。

#### 4.3.3 `delete` — 删除

请求：`{"cmd":"delete","key":"user:1001"}`
成功：`{"ok":true,"data":{"kind":"delete","deleted":true}}`
失败：键不存在时回 `NOT_FOUND`。

#### 4.3.4 `keys` — 列键

请求：`{"cmd":"keys"}`
成功：

```json
{"ok":true,"data":{"kind":"keys","keys":["config:engine","course:name"],"count":2}}
```

- `keys` 为**字典序**全量键列表；键很多时响应可能触发 `FRAME_TOO_LARGE`（键约束 256B × 数量 / 64KiB 上限）；前端处理已定（T-4）：超限时提示并建议减少键数量。

#### 4.3.5 `status` — 统计

请求：`{"cmd":"status"}`
成功：`{"ok":true,"data":{"kind":"status","count":2}}`

前端映射：指标条“键总数”、总览页键数。**注意**：仅返回 `count`；已决定不扩展（T-3），前端删除其余指标展示，见 4.4.3。

#### 4.3.6 `ping` — 探活

请求：`{"cmd":"ping"}`，成功：`{"ok":true,"data":{"kind":"ping"}}`。
前端映射：顶栏连接徽章、`ServerState` 推导、轮询心跳。

#### 4.3.7 `quit` — 关闭当前连接

请求：`{"cmd":"quit"}`，成功：`{"ok":true,"data":{"kind":"quit"}}`，随后服务端关闭该连接。
前端映射：接入层内部连接管理使用；页面逻辑一般不直接调用。

### 4.4 扩展接口与决策结果（T-2 ~ T-9 已全部落定，均不改变原设计意图）

以下小节按原待确认项编号保留，便于追溯：**需实施**的为 4.4.4（接入层压测器）、4.4.5（接入层进程托管），均由接入层承担，后端零改动；4.4.2 按组合命令实现（不扩展协议）；4.4.1、4.4.3 为**前端删除项**；4.4.6 ~ 4.4.8 **保留前端本地模拟**。

#### 4.4.1 `set` 支持 TTL（T-2 已定：不实现，前端删除）

**决策**：不扩展 TTL。前端需删除：

- TTL 输入框（`kv-ttl`）及 `performKvAction` 的 `ttlSeconds` 参数；
- `KvEntry.expiresAt` 字段、每秒扫描过期淘汰的定时器；
- 键卡片的 TTL 倒计时与“TTL n 秒”标签，全部键按“永久保存”展示。

原建议的 `ttlSeconds` 字段**作废**；发送该字段会因协议严格校验回 `EXTRA_ARGUMENT`。

#### 4.4.2 存储视图取值方式（T-4 已定：方案 A，组合命令）

**决策**：采用方案 A——`keys` 拿全量键名 → 按存储视图当前页逐键 `get` 取值；**不新增** `scan` 命令（方案 B 否决）。搜索过滤在前端对已取数据做（原型现有逻辑即前端过滤）。

键数量大到 `keys` 响应触发 `FRAME_TOO_LARGE` 时，前端提示“数据量超过协议上限”并建议减少键数量（与 6.2 一致）。

#### 4.4.3 指标与元信息（T-3 已定：不实现，前端删除）

**决策**：不扩展 `status`，后端仅继续使用现有 `count`。前端删除/调整：

- 全局指标条：删除“实时吞吐、累计请求、成功率、WAL 大小”，保留“键总数”（来自 `status.count`）；“活跃客户端”仅在压测期间由压测器状态提供，否则删除；
- 系统总览页：删除运行时长、版本、WAL 健康状况等服务端指标卡片内容；吞吐曲线仅在有压测数据时展示（数据来自 4.4.4 压测器），否则删除或置空状态；
- “最近请求流”与操作历史由前端在每次请求后自维护，不依赖后端。

原建议的 `status` 扩展字段（`qps`/`walRecords`/`uptimeSeconds` 等）**作废**；发送带多余字段的请求不会发生（`status` 无参数），但前端不得再展示这些指标。

#### 4.4.4 负载实验与基准测试（T-5 已定：接入层内置压测器）

**决策**：采用方案 A——压测器作为接入层（T-1 的服务端代理进程）的内部模块，收到控制指令后自行开 N 条 TCP 连接对后端发压，并汇总进度/结果；不改动 Rust 后端。候选方案 B（独立 bench）与 C（后端新增命令）否决。

接入层压测控制接口（已定形态）：

```
POST /api/experiment/start   {"type":"concurrency","clients":100,"requestsPerClient":100,"workload":"mixed"}
POST /api/experiment/stop    {"type":"concurrency"}
GET  /api/experiment/state   → {"status":"RUNNING","progress":42.5,"successful":4250,"failed":0,"throughput":8640,"elapsedSeconds":3.8}
POST /api/benchmark/start    {"scales":[1,10,50,100],"workload":"mixed"}
GET  /api/benchmark/state    → {"status":"RUNNING","progress":50,"points":[{"clients":1,"qps":1480,"p50":0.42,"p95":0.9,"p99":1.4,"success":100}]}
```

`workload` 枚举映射（T-11 已定）：`读取为主→read`，`写入为主→write`，`混合读写→mixed`。

压测副作用约定：

- 压测写入统一使用 `lab:key:` 前缀，会真实写入 `data/kv.wal`；演示结束后可逐键 `delete` 清理，或按 T-10 手动删除文件后重启服务；
- 压测期间后端被 kill 时，压测器捕获连接断开，将实验状态置为 `INTERRUPTED` 并保留已完成数据点（与原型行为一致）；
- `p50/p95/p99` 由压测器对每个请求的往返耗时排序取分位数，单位毫秒；`success` 为百分比。

#### 4.4.5 服务进程控制（kill / restart / 恢复进度）（T-6 已定：接入层托管子进程）

后端无远程关机/重启命令（`quit` 只关单条连接，符合原设计）。已定：

- 由**接入层负责进程托管**：接入层以子进程方式启动 `kv-server`，暴露：

```
POST /api/server/kill      → 强制终止子进程（对应前端“② 强制终止服务”）
POST /api/server/restart   → 重新拉起子进程（对应“③ 重启并重放 WAL”）
GET  /api/server/state     → {"state":"ONLINE"|"OFFLINE"|"STARTING"|"RECOVERING"|"ERROR"}
```

- `RECOVERING`/`STARTING` 判定（已定）：后端在恢复完成前不进入监听，“连接被拒”与“正在重放”无法区分；接入层按“**进程存活 + 端口未就绪**”统一显示恢复中；
- 重放进度条：后端无进度接口，前端按“`ping` 成功后读取 `status.count` 与崩溃前 `count` 的比值”一次性展示，过程动画由前端模拟（已定）。

#### 4.4.6 故障注入（T-7 已定：仅前端演示层模拟）

原型的“故障注入（恢复时故意丢 2 个键）”仅为展示 FAIL 状态。**已定**：只在前端/演示层实现（恢复完成后前端本地删除 2 个键再比对），不修改后端数据；真实后端行为始终以“全部恢复、校验通过”为准。

#### 4.4.7 WAL 压缩（Compact）（T-8 已定：本期不实现）

现有后端无 `compact` 命令，且设计文档明确“WAL 不在服务器退出时整体重写”；压缩与现有“追加式 + 损坏即拒绝启动”的约束存在设计边界冲突。
**决策**：本期不实现；前端保留原型的 Compact 面板但继续本地模拟，标注“扩展预留”；若未来实施，需先补充快照/原子替换的设计评审。

#### 4.4.8 发布订阅（Pub/Sub）（T-9 已定：本期不纳入）

后端完全没有发布订阅能力；原型页也标注“前端本地模拟 · 扩展预留”。
**决策**：本期不纳入、不联调，保留本地模拟；若未来实施，需要服务端推送通道（WebSocket，见 2.2 方案 B），消息结构建议：

```json
{"cmd":"subscribe","channel":"news"}
{"cmd":"publish","channel":"news","message":"Hello Rust"}
// 服务端推送帧（非一问一答，突破现有协议模型，需单独设计评审）
{"kind":"push","channel":"news","message":"Hello Rust"}
```

## 5. 核心数据模型与状态定义

### 5.1 后端协议数据模型（现有，权威）

```ts
// 请求（与 mvp/src/protocol.rs 的 Request 对应）
type Request =
  | { cmd: 'set'; key: string; value: string }
  | { cmd: 'get'; key: string }
  | { cmd: 'delete'; key: string }
  | { cmd: 'keys' }
  | { cmd: 'status' }
  | { cmd: 'ping' }
  | { cmd: 'quit' };

// 响应
type Response =
  | { ok: true; data: ResponseData }
  | { ok: false; error: { code: ErrorCode; message: string } };

type ResponseData =
  | { kind: 'set'; replaced: boolean }
  | { kind: 'get'; value: string }
  | { kind: 'delete'; deleted: boolean }
  | { kind: 'keys'; keys: string[]; count: number }
  | { kind: 'status'; count: number }
  | { kind: 'ping' }
  | { kind: 'quit' };
```

### 5.2 前端数据模型（原型现有，需与后端对齐处已标注）

```ts
type KvEntry = { key: string; value: string }; // TTL 已删除（T-2 已定），前端需移除 expiresAt
type OperationLog = { id: number; time: string; op: string; detail: string; latency: string; tone: OperationTone; result: string };
type BenchmarkPoint = { clients: number; qps: number; p50: number; p95: number; p99: number; success: number };
type Subscriber = { id: number; name: string; active: boolean; received: string[] }; // 仅本地模拟（T-9 已定）
type CompactResult = { beforeRecords: number; beforeBytes: number; afterRecords: number; afterBytes: number }; // 仅本地模拟（T-8 已定）
```

对齐要点：

| 前端模型                   | 对齐说明                                            |
| ---------------------- | ----------------------------------------------- |
| `KvEntry.expiresAt`    | T-2 已定：字段删除，前端移除 TTL 输入、倒计时与过期淘汰逻辑，全部键按“永久保存”展示 |
| `OperationLog.latency` | 后端不返回耗时；由接入层打点测量，或前端显示“—”                       |
| `BenchmarkPoint`       | 与 4.4.4 压测结果字段一一对应（T-5 已定）                      |
| `CompactResult`        | T-8 已定：本期不实现，保留本地模拟                             |

### 5.3 状态枚举与流转

```
ServerState:    ONLINE ⇄ OFFLINE；ONLINE → STARTING → RECOVERING → ONLINE；任意 → ERROR
                （推导规则见 2.3，后端无该概念，由接入层/前端维护）

ExperimentStatus（并发实验/性能测试）:
                IDLE → RUNNING → COMPLETED
                RUNNING → STOPPED（手动停止）
                RUNNING → INTERRUPTED（服务中断，保留已完成结果）

RecoveryPhase:  IDLE → PREPARED（写入快照）→ CRASHED（杀进程）→ RECOVERING（重启）→ VERIFIED（校验完成）
                重新写入快照可从任意阶段回到 PREPARED
```

前端按钮可用性必须跟随状态机（原型已实现，联调时保持）：

- “② 强制终止服务”仅在 `phase=PREPARED && serverState=ONLINE` 可用；
- “③ 重启并重放”仅在 `phase=CRASHED` 可用；
- 并发/基准测试“开始”仅在 `ONLINE` 可用。

## 6. 错误码、错误响应格式与前端处理建议

### 6.1 错误响应格式（现有后端）

```json
{"ok":false,"error":{"code":"NOT_FOUND","message":"key \"x\" does not exist"}}
```

### 6.2 错误码全集与前端处理建议

| 错误码                                                 | 触发场景                              | 前端处理建议                          | 对应原型反馈                  |
| --------------------------------------------------- | --------------------------------- | ------------------------------- | ----------------------- |
| `NOT_FOUND`                                         | GET/DELETE 的键不存在                  | 显示“未找到”错误卡片；不视为连接故障             | `KvResult.kind='error'` |
| `INVALID_KEY`                                       | 键为空/含空白或控制字符/超 256B               | 表单内联校验提示；**提交前先在前端拦截**          | 错误卡片                    |
| `INVALID_VALUE`                                     | 值为空/含控制字符/超 16 KiB                | 同上                              | 错误卡片                    |
| `MISSING_ARGUMENT`                                  | 缺 `cmd`/`key`/`value`             | 属前端 bug，记录并提示                   | 错误卡片                    |
| `EXTRA_ARGUMENT`                                    | 发送了未知字段（如 TTL 删除后仍发 `ttlSeconds`） | 属前端 bug；联调期重点回归                 | 错误卡片                    |
| `UNKNOWN_COMMAND`                                   | `cmd` 拼写错误                        | 属前端 bug                         | 错误卡片                    |
| `INVALID_JSON` / `INVALID_UTF8` / `INVALID_REQUEST` | 帧损坏                               | 接入层应保证不出现；出现则记录并提示重试            | 错误卡片                    |
| `FRAME_TOO_LARGE`                                   | 请求/响应超 64 KiB（如 `keys` 键过多、值过长）   | 提示“数据量超过协议上限”，建议删除部分键或缩小值       | 错误卡片                    |
| `STORAGE_ERROR`                                     | WAL 写入失败等运行时 IO 错误                | **置为 `ERROR` 状态**，禁止后续写入并提示人工检查 | 顶栏状态徽章变红                |
| `BACKEND_UNREACHABLE`（接入层）                          | 连接被拒/进程不存在                        | 置为 `OFFLINE`，引导到“崩溃恢复”页重启       | “连接失败”卡片（原型已有文案）        |

### 6.3 前端校验前置清单（与后端规则对齐，避免无效请求）

- 键：非空、不含空格/制表符/换行等空白与控制字符、`new TextEncoder().encode(key).length <= 256`；
- 值：非空、不含控制字符、字节数 ≤ 16384（**允许空格**，如 `"Rust 网络 KV 存储"`）；
- 原型现有“键不能为空 / 值不能为空”提示保留，其余规则为新增前端校验。

## 7. 网络异常、重试与超时

| 场景       | 约定                                                                                                                                     |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 健康探测周期   | 接入层/前端每 **2 秒** `ping` 一次；连续 **3 次**失败判定 `OFFLINE`（T-12 已定）                                                                            |
| 单请求超时    | 接入层对后端单请求读超时 **3 秒**（写操作含 `sync_data`，本地磁盘通常毫秒级；恢复期可能稍长）（T-12 已定）                                                                      |
| 重试策略     | 读命令（`get`/`keys`/`status`/`ping`）可安全重试 **1 次**；`set`/`delete` **不自动重试**（可能已落盘成功，重试不改变最终值但会破坏 `replaced`/`NOT_FOUND` 语义展示），失败直接提示用户重新执行 |
| 断线重连     | 接入层检测到后端连接断开后自动重建连接；重建成功后前端自动恢复 `ONLINE`                                                                                               |
| 恢复期请求    | `RECOVERING`/`OFFLINE` 状态下前端禁用全部写操作与实验按钮（原型已实现 `disabled` 逻辑，保持）                                                                       |
| 粘包/半包    | 由后端 `read_frame` 与接入层按行解析共同保证；浏览器侧无需处理                                                                                                 |
| 压测中的服务中断 | 并发实验/基准测试置为 `INTERRUPTED`/`STOPPED`，保留已完成数据点（与原型行为一致）                                                                                  |

## 8. 持久化与数据一致性要求

联调必须尊重后端已有的持久化契约（《协议与持久化设计》第 4、5 节）：

1. **先落盘后改内存**：`set`/`delete` 在共享锁内按“构造记录 → 追加 → `flush` → `sync_data` → 更新 BTreeMap → 返回”执行。前端收到成功响应时数据**必然已持久化**，可以放心在崩溃恢复实验中作为“崩溃前快照”依据。
2. **成功响应的含义**：`ok:true` 即保证该修改在重启后可恢复；任何持久化失败都会返回 `STORAGE_ERROR` 而不会假装成功。
3. **恢复语义**：重启后逐行重放 `data/kv.wal`；损坏（缺末尾 LF、非法 JSON、未知 `op` 等）时服务器**拒绝启动**并报告行号。前端“③ 重启”后若长时间无法 `ping` 通，应提示“可能检测到 WAL 损坏，请查看服务器日志”，而不是无限等待（该提示文案为默认建议，非阻塞项，可在前端实现时微调）。
4. **校验方式（崩溃恢复页）**：
   - 数量：恢复后 `status.count` == 崩溃前 `count`；
   - 抽样：对快照中的样本键逐个 `get` 比对值；
   - 指纹：前端对“键=值;”序列计算 FNV-1a 指纹（原型 `fingerprintFor` 算法保持不变，前后端不必一致，仅前端自比）。
5. **写并发一致性**：所有写经同一临界区串行化，WAL 顺序与内存顺序一致；并发实验中前端不得假设“读到自己刚写的值”之外的顺序（单连接内严格有序，跨连接只保证最终可见）。
6. **数据文件**：默认 `data/kv.wal`；联调与演示使用同一文件，`重置实验室`操作**不会**删除该文件（重置为纯前端状态重置，T-10 已定）；如需空库演示，手动删除文件后重启服务。

## 9. 联调步骤、测试要点与验收标准

### 9.1 环境准备

```powershell
# 1. 启动后端（在 mvp/ 目录）
cargo build
cargo run --bin kv-server            # 监听 127.0.0.1:7878，数据文件 data/kv.wal

# 2. 启动前端原型（在 prototype/ 目录，本地运行，不部署）
```

> 接入层为方案 A（T-1 已定）：在 `prototype` 工程服务端实现，随 `npm run dev` 一同启动；同时承担 `kv-server` 子进程托管（T-6）与压测器（T-5）。若由接入层接管进程托管，上述第 1 步的手动启动可改由接入层自动拉起。

### 9.2 联调步骤（按依赖顺序）

| 步骤  | 内容                                                                         | 依赖              |
| --- | -------------------------------------------------------------------------- | --------------- |
| S1  | 接入层打通：`POST /api/kv` 转发 `ping`，前端顶栏显示“服务在线”                                | 接入层实现完成（T-1 已定） |
| S2  | 键值操作页：SET/GET/DELETE/KEYS 全链路，覆盖新增、覆盖（`replaced`）、未找到；同步删除 TTL 输入与倒计时（T-2） | S1              |
| S3  | 存储视图：`keys` + 批量 `get` 渲染、搜索、分页（T-4 已定）                                    | S2              |
| S4  | 前端校验与错误码映射：6.2 表中每个错误码至少触发一次                                               | S2              |
| S5  | 崩溃恢复：快照 → 接入层 kill → restart → `ping`/`status`/抽样 `get` 校验（T-6/T-7 已定）     | S1              |
| S6  | 并发实验 / 性能测试：压测控制与结果图表（T-5/T-11 已定）                                         | S1              |
| S7  | 总览页/指标条调整：删除非 count 指标（T-3），接入 `status.count` 与压测器汇总数据                     | S2，S6           |
| S8  | 离线/异常演练：服务未启动、恢复中、WAL 损坏三种状态下的前端表现                                         | S5              |

### 9.3 测试要点

- **一问一答**：同一连接连续发送多条请求，每条都得到恰好一条响应；
- **错误后继续**：发送非法帧（如 `{"cmd":"foo"}`）后连接仍可用；
- **上限边界**：256 字节键、16 KiB 值写入成功；257 字节键回 `INVALID_KEY`；
- **帧超限**：插入大量键后 `keys` 返回 `FRAME_TOO_LARGE`，前端正确提示；
- **并发安全**：并发实验中 `status.count` 与成功写入数一致，无 `STORAGE_ERROR`；
- **断电恢复**：S5 全流程后数量/抽样/指纹三项校验全部通过；损坏样例（手工截断 `kv.wal` 末行一半）启动失败且前端给出提示；
- **隔离性**：一个浏览器标签页发送非法请求不影响其他标签页。

### 9.4 验收标准

1. 键值操作页四类操作全链路可用，错误反馈与 6.2 表一致；
2. 崩溃恢复实验可完整走通五步（准备数据→强制断电→重启→重放→校验）且校验通过；人为损坏 WAL 时明确报错而非静默；
3. 服务离线时全部写操作与实验按钮禁用，顶栏与页面状态一致；恢复在线后自动可用；
4. 并发/性能实验的结果数值来自接入层压测器的真实压测（T-5 已定），禁止把原型写死的 `baselineBenchmark` 当作实测结果展示（与《需求规格与验收》“不能把未执行的测试写成已通过”一致）；
5. T-2/T-3 相关前端元素（TTL 输入与倒计时、非 count 指标）已删除；T-8/T-9 等本期不实施的能力保留本地模拟并明确标注“本地模拟/扩展预留”；
6. 《需求规格与验收》第 5 节命令（`cargo fmt --check`、`clippy -D warnings`、`cargo test`、`cargo build`）全部通过。
