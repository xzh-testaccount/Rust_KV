# 前后端对接文档

> 本文以前端产品原型（`prototype/app/page.tsx`）的页面与交互为主要依据，结合《架构设计》《协议与持久化设计》《需求规格与验收》以及后端实现（`src/protocol.rs`、`src/server.rs`、`src/controller.rs` 等）整理，供前后端联调与验收使用。
> 
> - 文档状态：**真实联调完成版**（v1.1，2026-09-02）。具体启动和现场验收以《P-06真实后端验收》为准。
> - 后端基线：TCP JSON Lines 协议，9 个固定命令（`set`/`get`/`delete`/`keys`/`status`/`storage_status`/`compact`/`ping`/`quit`）
> - 前端基线：`prototype` 原型，6 个页面（系统总览 / 键值操作 / 并发实验 / 崩溃恢复 / 性能测试 / 发布订阅）；**答辩主流程收敛为 CRUD → 基础并发 → 崩溃恢复/WAL → 性能实验室**，发布订阅仅保留扩展预留。
> - P-06 已落地：`sync/async × mutex/rwlock` 四种组合、Snapshot + 增量 WAL、在线 Compact、Rust HTTP 控制器、真实并发、真实强杀恢复和隔离 Benchmark 均已实现。答辩模式请求失败时直接报错，不回退到模拟数据。

## 1. 文档目标与适用范围

### 1.1 目标

1. 明确前端原型每个页面、每类交互所需的数据与后端能力；
2. 给出前后端之间的请求/响应格式、字段定义、错误码与状态约定；
3. 作为联调执行、问题定位和最终验收的共同依据。

### 1.2 适用范围

- 前端：`prototype/` 下的可视化实验平台（本地启动、本地访问，不部署）；
- 后端：`src/` 下的 Rust KV 服务器（默认 `127.0.0.1:7878`，数据文件 `data/kv.wal`）；
- 中间接入层：Rust `kv-controller` 监听 `127.0.0.1:7879`，Vite 将浏览器 `/api` 请求代理给控制器。

### 1.3 术语约定

| 术语       | 含义                                                                     |
| -------- | ---------------------------------------------------------------------- |
| 帧（frame） | 一条以 LF 结尾的 UTF-8 JSON 行，逻辑上限 64 KiB                                    |
| 接入层      | 位于浏览器与 Rust 服务之间的代理（HTTP/WebSocket），见第 2 章                             |
| 原型模拟     | 只用于脱离后端检查页面布局和状态机；答辩模式中的 CRUD、Compact、并发、崩溃恢复和性能实验均不得用模拟数据替代真实结果 |

## 2. 接入架构（联调前提）

### 2.1 现状与约束

- 后端协议是 **TCP + JSON Lines**（`protocol.rs` 中 `read_frame`/`parse_request_bytes`），一问一答，单连接可连续多帧。
- 浏览器环境**不能**直接建立裸 TCP 连接；原型页面注释也明确写着“所有交互均为本地原型模拟，不连接后端”。
- 因此必须有一个接入层把浏览器的调用翻译成 TCP JSON Lines。

### 2.2 已落地的接入方案

| 方案           | 说明                                                                                                | 决策（T-1）                               |
| ------------ | ------------------------------------------------------------------------------------------------- | ------------------------------------- |
| Vite 同源代理 | 浏览器请求 `/api/*`，Vite 转发至 `127.0.0.1:7879` | ✅ 已实现 |
| Rust 控制器 | `kv-controller` 提供 HTTP API，并代理 TCP JSON Lines、托管子进程和执行实验 | ✅ 已实现 |
| KV 服务 | `kv-server` 在 `127.0.0.1:7878` 提供真实存储能力 | ✅ 已实现 |

> 最终链路为：浏览器 → Vite `/api` 代理 → Rust 控制器 → `kv-server`。控制器同时负责真实 Kill/Restart、并发实验和 Benchmark，浏览器不直接管理系统进程。

### 2.3 连接与状态模型

- 前端以 `ping` 命令作为健康探测（后端返回 `{"ok":true,"data":{"kind":"ping"}}`）；
- `ServerState` 由前端根据探测结果与实验阶段推导：

| 前端状态         | 推导规则（T-6 / T-12 已定）                      |
| ------------ | ---------------------------------------- |
| `ONLINE`     | 最近一次 `ping` 成功                           |
| `OFFLINE`    | 连接失败/超时，或执行了“强制终止服务”                     |
| `STARTING`   | 进程刚拉起、端口尚未就绪（T-6 已定）                     |
| `RECOVERING` | 重启后进程存活但端口未就绪（Snapshot 加载 / WAL 重放中），统一显示“恢复中”（T-6 已定） |
| `ERROR`      | 连接成功但连续返回 `STORAGE_ERROR` 等不可恢复错误        |

### 2.4 主演示服务与性能实验目标隔离（T-16 已定）

为避免性能实验污染 CRUD / 崩溃恢复所使用的 `data/kv.wal`，接入层维护两类后端目标：

| 目标             | 用途                       | 默认监听             | 数据文件                  |
| -------------- | ------------------------ | ---------------- | --------------------- |
| 主演示服务          | CRUD、基础并发、崩溃恢复           | `127.0.0.1:7878` | `data/kv.wal`         |
| Benchmark 临时服务 | Performance Lab 的单次/对照实验 | 由接入层选择空闲本地端口     | 独立临时 WAL（每个 Run 单独文件） |

- Performance Lab **不直接对主演示服务发压**；接入层为每个 Benchmark Run 启动独立的 `kv-server` 目标，运行结束后回收。
- A/B 对照实验必须从同一份预置数据基线复制出两个独立 WAL，确保实验组与对照组初始状态一致；前一组写入不得污染后一组。
- Benchmark 目标固定为 `localhost`，不把公网、代理或远端网络波动引入本轮系统实现对比。
- 主演示服务的在线/离线状态与 Benchmark 临时服务状态分开维护；Performance 页面显示当前 Benchmark Target 状态，不能把临时目标误显示为主演示服务状态。

## 3. 前端原型功能梳理与后端接口映射

### 3.1 页面入口与主要用户操作流程

原型为单页应用。顶栏长期只承担**主演示服务状态**与`status.count`（本地键总数）等真实可得信息；吞吐、P50/P95/P99 等性能指标只在实验运行期间由实验执行器提供，不再作为伪实时全局指标。

答辩主流程固定为：

1. **键值操作**：完成 SET / GET / UPDATE（再次 SET）/ DELETE / KEYS，证明基础功能正确；
2. **并发实验**：让多个真实 TCP 客户端同时工作，关注完成数、成功/失败和客户端活动状态，证明并发正确性；
3. **崩溃恢复**：写入测试数据 → 强制终止服务 → Snapshot / WAL 保留 → 重启并恢复 → 使用前端 Verification Snapshot 自动校验；
4. **性能实验室**：在固定数据集、持久化语义、协议和网络条件下，通过单次实验/对照实验研究 `Sync vs Async`、`Mutex vs RwLock`、不同读写负载对吞吐与尾延迟的影响。

| 页面   | 主操作流程                                                                                                                                                                  |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 系统总览 | 纯展示：主演示服务在线状态、键总数、最近 CRUD/并发/恢复/性能实验结果摘要；不伪造服务端不存在的 QPS/WAL/版本/运行时长指标                                                                                                  |
| 键值操作 | 填写键/值 → SET / GET / DELETE / KEYS → 结果卡片反馈；再次 SET 即 UPDATE；右侧真实存储视图同步更新                                                                                                |
| 并发实验 | 配置客户端数量（1/10/50/100）、每客户端请求数、负载类型 → 启动真实多连接实验 → 观察 Client Grid、完成进度、成功/失败 → `CONCURRENCY PASS/FAIL`；性能数字仅作辅助或删除                                                        |
| 崩溃恢复 | ① Seed 测试键并记录 **Frontend Verification Snapshot** → ② 接入层强制终止主演示服务 → ③ 确认 Memory Store 消失而 Snapshot / WAL 文件保留 → ④ 重启，后端加载 Snapshot 并重放增量 WAL → ⑤ `status`/`keys`/`get` 与前端校验快照比对，输出 PASS/FAIL |
| 性能测试 | 选择单次/对照实验 → 选择 Runtime、Lock、Workload、并发规模 → 接入层启动隔离 Benchmark Target → 每个 Scale 真实发压并逐点返回 QPS/P50/P95/P99 → 对照模式自动计算差异并基于实测数据生成结论                                      |
| 发布订阅 | 不纳入本期答辩主流程；保留“扩展预留”页面，不参与真实联调与验收                                                                                                                                       |

全局交互：`重置实验室` 只重置前端/接入层实验状态，不删除主演示 Snapshot/WAL；服务离线时 CRUD、基础并发等入口禁用并引导到“崩溃恢复”页。Performance Lab 的 Benchmark Target 独立于主演示服务。

### 3.2 需要展示、创建、修改、删除或查询的数据

## 4. 接口与协议定义

### 4.1 传输层约定（现有后端，不变）

| 项    | 约定                                                                        |
| ---- | ------------------------------------------------------------------------- |
| 传输   | TCP，默认 `127.0.0.1:7878`（服务端可用 `--bind`/`--data` 覆盖）                       |
| 编码   | UTF-8 JSON Lines，每请求/响应一行，以 LF 结尾（接受 CRLF）                                |
| 帧上限  | 65,536 字节（不含结尾 LF）；超限请求回 `FRAME_TOO_LARGE`，超限响应同样回 `FRAME_TOO_LARGE`，不得截断 |
| 一问一答 | 每条请求恰好一条响应；单条请求错误不断开连接                                                    |
| 键约束  | 非空，不含空白字符/控制字符，UTF-8 ≤ 256 字节                                             |
| 值约束  | 非空，不含控制字符（允许空格），UTF-8 ≤ 16 KiB                                            |

### 4.2 接入层对浏览器暴露的 HTTP 接口（T-1 已定）

采用“单一命令代理端点”，接入层只负责把 JSON 请求转成一行发给后端并把响应行解析为 JSON 返回，不做业务改写：

```
POST /api/kv
Content-Type: application/json

{"cmd":"get","key":"course:name"}
```

响应即后端原始响应对象：

```json
{"ok":true,"data":{"kind":"get","value":"Rust 网络 KV 存储"}}
```

- 接入层网络/进程级故障时返回 HTTP 5xx 与统一错误体：

```json
{"ok":false,"error":{"code":"BACKEND_UNREACHABLE","message":"connect 127.0.0.1:7878 refused"}}
```

> `BACKEND_UNREACHABLE` 是**接入层新增码**，不在后端 11 个错误码之列；前端处理建议见第 6 章。**该端点形态已确认（T-1）。**

### 4.3 现有后端命令定义（已实现，联调直接可用）

#### 4.3.1 `set` — 写入（新增或覆盖）

请求：

```json
{"cmd":"set","key":"user:1001","value":"Alice"}
```

成功响应：

```json
{"ok":true,"data":{"kind":"set","replaced":false}}
```

| 字段         | 类型     | 说明            |
| ---------- | ------ | ------------- |
| `key`      | string | 必填；约束见 4.1    |
| `value`    | string | 必填；约束见 4.1    |
| `replaced` | bool   | 响应字段：是否覆盖了已有键 |

前端映射：键值操作页“写入 SET”。`replaced=true` 显示“已更新”，`false` 显示“已创建”。
**注意**：TTL **不支持**（T-2 已定）；前端需删除 TTL 输入框与 `expiresAt` 相关逻辑，`set` 请求只保留 `key`/`value` 字段，发送 `ttlSeconds` 等多余字段会触发 `EXTRA_ARGUMENT`。

#### 4.3.2 `get` — 读取

请求：`{"cmd":"get","key":"user:1001"}`
成功：`{"ok":true,"data":{"kind":"get","value":"Alice"}}`
失败（键不存在）：`{"ok":false,"error":{"code":"NOT_FOUND","message":"key \"user:1001\" does not exist"}}`

前端映射：GET 按钮；命中时把 `value` 回填到 Value 输入框；`NOT_FOUND` 显示“未找到”错误卡片。

#### 4.3.3 `delete` — 删除

请求：`{"cmd":"delete","key":"user:1001"}`
成功：`{"ok":true,"data":{"kind":"delete","deleted":true}}`
失败：键不存在时回 `NOT_FOUND`。

#### 4.3.4 `keys` — 列键

请求：`{"cmd":"keys"}`
成功：

```json
{"ok":true,"data":{"kind":"keys","keys":["config:engine","course:name"],"count":2}}
```

- `keys` 为**字典序**全量键列表；键很多时响应可能触发 `FRAME_TOO_LARGE`（键约束 256B × 数量 / 64KiB 上限）；前端处理已定（T-4）：超限时提示并建议减少键数量。

#### 4.3.5 `status` — 统计

请求：`{"cmd":"status"}`


```
POST /api/server/restart   → 重新拉起子进程（对应“③ 加载 Snapshot 并重放增量 WAL”）
```

#### 4.4.7 Snapshot 与 WAL 压缩（Compact）（T-8 已实现）

主演示服务提供 `storage_status` 与 `compact` 两个真实 TCP 命令，控制器将其封装为：

```text
GET  /api/storage/state    → 当前 entries、WAL/Snapshot 字节数、记录数、lastSequence、writable
POST /api/storage/compact  → 执行 Compact，返回 before/after 和 compactMs
```

`compact()` 的安全顺序为：从内存生成带 CRC32 和 `last_seq` 的 Snapshot → 写临时文件并同步 → 原子发布 Snapshot（保留 `.bak`）→ 截断并同步已被快照覆盖的 WAL。程序若在中间崩溃，启动恢复会使用已发布的有效 Snapshot，并忽略未发布的临时文件；损坏文件不会被静默覆盖。

页面同时展示两类证据：固定负载下基础版与创新版的历史实测柱状图，以及当前服务执行 Compact 后返回的实时 before/after 数据。历史数据必须注明环境和负载，不能冒充本次实时结果。

### 4.4.8 Performance 后端实现矩阵（T-15 已定：真实后端能力，不允许模拟）

Performance Lab 已具备以下四种可启动组合：

| Runtime | Lock | 状态 | 语义要求 |
| --- | --- | --- | --- |
| `sync` | `mutex` | ✅ 已实现 | `std::net` + 一连接一线程；所有 Store 访问互斥 |
| `sync` | `rwlock` | ✅ 已实现 | GET/KEYS/STATUS/STORAGE_STATUS 读锁；SET/DELETE/COMPACT 写锁 |
| `async` | `mutex` | ✅ 已实现 | Tokio 网络任务；阻塞存储操作走 `spawn_blocking` |
| `async` | `rwlock` | ✅ 已实现 | Tokio 网络任务 + 读写锁语义 |

建议统一进程启动契约：

```powershell
kv-server --bind 127.0.0.1:<port> --data <wal-path> --runtime sync --lock mutex
kv-server --bind 127.0.0.1:<port> --data <wal-path> --runtime async --lock rwlock
```

其中 `--runtime` / `--lock` 为本版新增 CLI；四种组合共享同一套 9 个 TCP JSON Lines 命令及响应结构。

实现约束：

- 所有四种组合必须保持**相同持久化契约**：SET/DELETE 均为 WAL append → `flush` → `sync_data` → 更新内存 → success；
- `RwLock` 只改变共享 Store 的锁策略，不能改变 WAL 语义；
- Async 只改变网络并发模型。由于现有 `File::sync_data` 是阻塞 I/O，Async 实现不得在 Tokio I/O worker 上长时间直接执行阻塞持久化；应使用 `spawn_blocking` 或等价的专用阻塞执行路径；
- `ping` 不需要 Store 锁；GET/KEYS/STATUS/STORAGE_STATUS 在 RwLock 模式下走读锁，SET/DELETE/COMPACT 走写锁；
- 四种组合均已通过网络与持久化集成测试，`/api/benchmark/capabilities` 返回全部可用。

#### 4.4.10 Benchmark 隔离与控制变量规则（T-16 ~ T-18）

Benchmark Runner 必须保证：

1. **隔离数据文件**：性能实验不写主演示 `data/kv.wal`；每个 Run 使用独立临时 WAL。
2. **相同初始状态**：先生成一份不计时的 Baseline WAL，A/B 从该文件复制出各自 Run WAL。
3. **相同随机序列**：相同 Scale 使用同一 `seed`，确保操作序列一致。
4. **相同持久化语义**：`WAL + flush + sync_data` 为只读固定条件，不能作为性能开关。
5. **相同协议与网络**：均使用 JSON Lines、localhost。
6. **只改变一个研究变量**：Compare 模式由接入层校验，不由前端文案自证。
7. **固定条件只读展示**：页面可显示 Dataset Size、Value Size、Requests/Scale、Persistence、Protocol、Network、Seed，但除 `requestsPerScale`/Scale 外不得在同一对照实验中临时修改。
8. **结论中立**：真实结果可能表现为 Async/RwLock 提升有限或变慢；这仍是有效实验结果，不得篡改或隐藏。

### 5.3 状态枚举与流转

```text
ServerState:
  ONLINE ⇄ OFFLINE
  ONLINE → STARTING → RECOVERING → ONLINE
  任意 → ERROR

ConcurrencyStatus:
  IDLE → RUNNING → COMPLETED
  RUNNING → STOPPED
  RUNNING → INTERRUPTED / FAILED

BenchmarkStatus:
  IDLE → PREPARING → RUNNING → COMPLETED
  RUNNING → STOPPED
  PREPARING/RUNNING → INTERRUPTED / FAILED

CompareRun:
  PREPARING_BASELINE
    → RUN_A
    → RESET_TO_BASELINE
    → RUN_B
    → COMPARING
    → COMPLETED

RecoveryPhase:
  IDLE
    → PREPARED        // Seed 完成，Verification Snapshot 已记录
    → CRASHED         // 主演示进程被强制终止；内存状态消失
    → RECOVERING      // 重启，后端只从持久化 Snapshot + 增量 WAL 恢复
    → VERIFIED        // status/keys/get 与 Frontend Verification Snapshot 校验完成
```

按钮/选项规则：

- “强制终止服务”仅在 `PREPARED && ServerState=ONLINE` 可用；
- “重启并重放”仅在 `CRASHED` 可用；
- 基础并发“开始”仅在主演示服务 `ONLINE` 时可用；
- Performance Lab 只在 Benchmark Runner 空闲时可启动新实验；
- `async` / `rwlock` 只有 capabilities 返回 `available=true` 才可选；
- Compare 模式开始前必须通过“单变量差异”校验；
- A/B 运行期间参数锁定，切换页面不取消实验；
- STOP/INTERRUPTED 后保留所有已完成 Scale 数据点。

## 8. 持久化与数据一致性要求

联调必须尊重后端已有的持久化契约（《协议与持久化设计》第 4、5 节）：

1. **先落盘后改内存**：所有 Runtime/Lock 变体都必须保持“构造记录 → 追加 → `flush` → `sync_data` → 更新 BTreeMap → 返回”的持久化语义。前端收到成功响应时该修改具备重启恢复依据。
2. **成功响应的含义**：`ok:true` 即保证该修改在重启后可恢复；任何持久化失败都会返回 `STORAGE_ERROR` 而不会假装成功。
3. **恢复语义**：重启后先校验并加载持久化 Snapshot，再按 `seq` 顺序重放其后的增量 WAL；Snapshot/WAL 的 CRC32、序号、格式或末尾完整性异常时服务器**拒绝启动**并给出明确错误。前端“③ 重启”后若长时间无法 `ping` 通，应提示“可能检测到持久化文件损坏，请查看服务器日志”，而不是无限等待。
4. **两种 Snapshot 的边界**：持久化 Snapshot 是后端生成的恢复来源；`FrontendVerificationSnapshot` 是浏览器在崩溃前记录的校验基线。**Restart 接口不得携带前端基线，也不得用它回灌数据**。
5. **校验方式（崩溃恢复页）**：
   - 数量：恢复后 `status.count` == 崩溃前 `count`；
   - 抽样：对快照中的样本键逐个 `get` 比对值；
   - 指纹：前端对“键=值;”序列计算 FNV-1a 指纹（原型 `fingerprintFor` 算法保持不变，前后端不必一致，仅前端自比）。
6. **写并发一致性**：所有写经同一临界区串行化，WAL 顺序与内存顺序一致；并发实验中前端不得假设“读到自己刚写的值”之外的顺序（单连接内严格有序，跨连接只保证最终可见）。
7. **数据文件**：默认 WAL 为 `data/kv.wal`，Snapshot 位于同目录的配套文件；`重置实验室`操作**不会**删除这些文件（重置为纯前端状态重置，T-10 已定）。如需空库演示，应先停止服务并明确删除整组演示数据文件。
8. **性能实验持久化公平性**：Benchmark 的 Sync/Async、Mutex/RwLock 对比不得关闭 `sync_data` 或替换为不同 WAL 策略；否则比较的是不同耐久性语义，结果不能标为同一控制变量实验。

### 9.3 测试要点

- **协议兼容**：9 个命令与错误码在 Sync/Async、Mutex/RwLock 四种组合下保持一致；
- **基础并发正确性**：1/10/50/100 客户端均能完成请求；一个客户端错误不影响其他连接；页面 PASS/FAIL 与真实计数一致；
- **RwLock 语义**：Read Heavy 下能观察多个读操作并发；写操作仍独占；不得让 WAL 与 BTreeMap 顺序分离；
- **Async 语义**：使用真实 Tokio 网络路径；阻塞 `sync_data` 不直接长期占用 Tokio I/O worker；
- **四实现组合**：`sync+mutex`、`sync+rwlock`、`async+mutex`、`async+rwlock` 使用相同 9 命令、相同持久化语义并通过既有功能测试；
- **Crash Recovery**：强制终止后浏览器校验基线仍在，但 Restart 请求中不携带任何恢复数据；后端只从有效持久化 Snapshot 与增量 WAL 恢复；
- **Compact 安全性**：压缩后 WAL 只保留快照之后的增量记录；重新启动所得键值状态与压缩前一致；损坏 Snapshot、WAL 序号缺口或 CRC32 错误均不得静默忽略；
- **Benchmark 隔离**：性能实验的 WAL 路径与 `data/kv.wal` 不同，运行前后主演示库数据不被污染；
- **控制变量**：Compare 模式除声明的 `variable` 外，其余 scenario/fixedConditions 完全一致；违规请求返回 `INVALID_EXPERIMENT_CONFIG`；
- **可复现序列**：A/B 同一 Scale 使用相同 seed，生成相同 GET/SET 序列；
- **Workload**：Read Heavy=90/10、Mixed=50/50、Write Heavy=10/90，且仅由 GET/SET 构成；
- **统计正确性**：`qps = completedRequests / elapsed`（失败请求通过 `success` 单独体现）；P50/P95/P99 来自该 Scale 已完成请求 RTT 样本，单位 ms；
- **中断保留**：后续 Scale 或 B Run 失败时，前面已完成的 points 不得清空；
- **结果中立**：若 Async/RwLock 实测没有提升，UI 仍原样展示，不改写为预设“优化成功”。

### 9.4 验收标准

1. CRUD 页面真实完成 SET / GET / UPDATE / DELETE / KEYS，Store View 与主演示服务一致；
2. 基础并发页使用真实多 TCP 连接，能演示 1/10/50/100 客户端并输出 `CONCURRENCY PASS/FAIL`；该页不承担主要性能结论；
3. 崩溃恢复完整走通 Seed → Kill → Restart → Snapshot Load + WAL Replay → Verify；前端校验基线只做比较，后端恢复来源只能是持久化文件；
4. `GET /api/benchmark/capabilities` 能准确反映四种 Runtime/Lock 组合的真实可用性；未实现组合前端禁用，禁止模拟冒充；
5. Performance Lab 支持 `single` 与 `compare` 两种模式；Compare 模式能对 Runtime、Lock、Workload 做**单变量** A/B；
6. 标准实验 Preset 可直接执行：`Sync vs Async`、`Mutex vs RwLock (Read Heavy)`、`Read Heavy vs Mixed vs Write Heavy`；
7. 每个 Benchmark Scale 返回真实 `qps/p50/p95/p99/success/elapsedMs`，并在图表中逐点追加；
8. A/B 实验使用相同 Baseline WAL、相同 Dataset/Value Size/Requests/Persistence/Protocol/Network/Seed；Benchmark 不污染主演示 `data/kv.wal`；
9. 页面展示 Throughput 与 P50/P95/P99 对比、百分比差异；结论仅根据真实数据生成，不预设 Async/RwLock 必然更快；
10. Benchmark 中断后保留已完成点并可重试失败 Scale；
11. B 存储提高项必须能通过真实 API 展示当前 Snapshot/WAL 状态与 Compact 的 before/after；基础版和统一 benchmark 只保存在实验分支，不进入主演示代码；
12. 历史对比柱状图必须注明固定负载、环境和统计口径，并与当前实时 Compact 结果分开展示；
13. 后端所有实现组合最终均通过现有格式化、Clippy、单元/集成测试和构建门禁；旧 `baselineBenchmark`/纯前端定时器不得作为实测证据。

- 原型 `KvAction = 'SET' | 'GET' | 'DELETE' | 'KEYS'` 与后端 `set/get/delete/keys` 一一对应（大小写不同，接入层转换）；

- 后端统一执行键和值校验并返回 `INVALID_KEY`/`INVALID_VALUE`；前端将真实错误显示给用户；
- 原型版本显示 `v0.3.0`、存储引擎 `BTreeMap + WAL`：存储引擎描述与后端实现相符；版本号无后端来源（代码中未见版本字段），按 T-3 决策属删除范围。
- 当前真实后端提供 Sync（一连接一线程）和 Async（Tokio task）两种网络模型，存储可选择 Mutex 或 RwLock；四种组合均可作为 Benchmark 被测目标。
