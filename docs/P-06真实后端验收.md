# P-06 答辩模式真实后端指南

## 1. 最终链路

```text
答辩网页 http://127.0.0.1:3000
  ↓ /api/*（Vite 同源代理）
本地实验控制器 127.0.0.1:7879
  ↓ TCP JSON Lines / 子进程管理
kv-server 127.0.0.1:7878
  ↓
BTreeMap + Snapshot + 增量 WAL + CRC32 + flush + sync_data
```

控制器和 KV 服务都只监听本机。网页不能直接操作进程，因此由控制器负责启动、强杀、重启、并发压测和基准测试。

## 2. 真实性边界

系统保留两种明确隔离的模式：

- 纯前端模式：只用于开发 UI，所有结果均标记“非实测”。
- 答辩模式：只展示 `/api/*` 返回的真实结果。

答辩模式遵守 Fail Closed：

- 后端未启动或断开时显示 `BACKEND_UNREACHABLE`；
- 实验失败时显示真实错误并保留已完成数据；
- 没有结果时显示空状态；
- 不生成 QPS、延迟、并发计数、WAL Replay、指纹或恢复进度；
- 不会因请求失败自动切回纯前端模拟。

## 5. 答辩四段演示

### 5.1 CRUD

在“键值操作”依次演示：

1. SET 新键；
2. GET 返回值；
3. SET 同键并显示覆盖；
4. KEYS 显示字典序存储视图；
5. DELETE 后再次 GET，显示 `NOT_FOUND`；
6. 再执行合法命令，证明单条错误不会断开服务。

写成功的含义是 WAL append、CRC32、flush 和 `sync_data` 已完成，然后才更新 BTreeMap。

### 5.2 Concurrency

在“并发实验”使用默认的 10 Clients、每客户端 100 Requests 和 Mixed 后开始；需要扩大规模时再选择 100 Clients。

页面只以真实状态给出结论：

```text
completed == total
successful == total
failed == 0
→ CONCURRENCY PASS
```

该页只证明并发正确性，不承担性能结论。

### 5.3 Crash Recovery

按页面顺序执行：

1. `Seed Data + Before`：控制器真实写入，返回 Before Count/Fingerprint；
2. `Kill Server`：操作系统强制终止真实子进程，内存 BTreeMap 消失，Snapshot 与 WAL 保留；
3. `Restart + Snapshot / WAL Replay`：新进程执行 `PersistentStore::open()`，先校验并加载 Snapshot，再重放连续序号更新的 WAL；
4. 控制器重新读取全部键值，计算 After Count/Fingerprint 和 lost。

通过标准：

```text
Before Count == After Count
Before Fingerprint == After Fingerprint
lost == 0
verified == true
```

控制器保存的 Before 只用于比较，重启接口不接收任何 Before 数据；恢复来源只能是后端持久化的 Snapshot 与 WAL。

### 5.4 Performance Lab

两档实验始终共享以下条件：

```text
10,000 Keys
128 B Value
JSON Lines over localhost TCP
WAL + flush + sync_data
Seed = 20260902
```

页面默认使用“快速演示”，答辩现场一次典型 A/B 的执行顺序为：

```text
A · 1 Client      → 固定采样 3 秒
A · 128 Clients   → 固定采样 3 秒
POST /api/benchmark/reset，并等待 ready + 新 resetEpoch
B · 1 Client      → 固定采样 3 秒
B · 128 Clients   → 固定采样 3 秒
```

快速档没有前端生成的性能数据。每个点由真实 Rust Benchmark Target 发压，完成后立即追加到执行序列和图表；任一点失败就进入 `INTERRUPTED`，不发布失败点，也不会切换到模拟曲线。典型两组 A/B 的目标等待时间约为 10～20 秒。

需要报告数据时切换“完整实验”：

```text
10,000 Requests / measured run
Clients = 1 / 10 / 50 / 100
Warmup × 1
Measured × 5
```

完整档继续生成充分采样和可归档证据；快速档证据会明确记录 `benchmark_profile=quick`、`sampling_mode=fixed_duration` 和 `sample_duration_ms=3000`，不会冒充完整实验。

建议主展示两个控制变量实验：

| 实验 | 只改变 | 固定条件 |
| --- | --- | --- |
| A：Sync vs Async | Runtime | Mutex、Mixed、相同请求序列 |
| B：Mutex vs RwLock | Lock | Async、Read Heavy、相同请求序列 |

工作负载对比可作为补充。结果无论是否符合理论预期都原样展示，不调整公式或隐藏结果。

每个 Scale 都生成独立证据目录；完整档包含 5 个正式采样文件，快速档包含 1 个固定时长采样文件：

```text
artifacts/benchmark-*/
  environment.json
  config.json
  raw/run-01.json ... run-05.json
  summary.json
```

证据中包含 Git commit、系统、CPU、Rust 版本、Runtime、Lock、Workload、请求数、成功/失败、QPS 和延迟分位。

### 5.5 B 数据层提高项

Performance Lab 底部同时展示：

- 基础 WAL 与 Snapshot + WAL 压缩的四项历史实测柱状对比；

历史图使用固定的 2,000 次 SET、100 个最终键、5 轮 release 实测结果，每个指标独立尺度并标明日期。它不随当前进程变化；实时面板的数据来自 `/api/storage/*`，二者不会混用。

## 6. 四种服务器组合

手动启动示例：

```powershell
cargo +stable-x86_64-pc-windows-gnu run --bin kv-server -- `
  --runtime async `
  --lock rwlock `
  --bind 127.0.0.1:7878 `
  --data data/kv.wal
```

- Sync：每连接一个系统线程。
- Async：每连接一个 Tokio 任务，阻塞持久化通过 `spawn_blocking` 执行。
- Mutex：所有存储操作互斥。
- RwLock：GET/KEYS/STATUS/STORAGE_STATUS 共享读锁，SET/DELETE/COMPACT 独占写锁。

四种组合不改变协议和持久化语义。

## 8. 故障排查

- `找不到 kv-server`：先执行 `cargo build --bins`。
- `BACKEND_UNREACHABLE`：检查控制器终端日志，以及 7878/7879 端口是否被占用。
- `WAL 损坏`：服务器会拒绝启动且不会覆盖文件，按日志行号检查，不要直接清空问题文件。
- `Snapshot 损坏`：服务器会报告 `Snapshot损坏` 并保留原文件；正式文件缺失但 `.bak` 存在时会尝试恢复备份。
- 前端依赖安装失败：确认网络可访问 npm，或开启本机代理后重新执行 `npm ci`。
- 正式 Performance Lab 较耗时：10k 请求、5 次正式轮次和 `sync_data` 都是真实执行；答辩前应预跑并保留证据包。
