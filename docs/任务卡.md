待开发：创新扩展与答辩展示
=============

Summary
-------

在现有 Rust KV 系统已完成 CRUD、TCP、多客户端并发、WAL 持久化、重启恢复与异常处理的基础上，新增以下扩展能力：

1. TTL 键过期

2. WAL Compact 日志压缩

3. 服务器并发压力测试

4. 轻量 Web Dashboard

目标不是扩展成完整数据库产品，而是围绕当前架构补充“可过期、可压缩、可量化、可观测”四项能力，用于课程答辩展示与创新性说明。

不得破坏现有协议、持久化可靠性和自动化测试。

* * *

W-01 TTL 键过期
------------

### 目标

支持带过期时间的 KV 数据，并保证服务器重启后 TTL 语义仍然正确。

### Implementation

新增类似：
    setex <key> <ttl_seconds> <value>ttl <key>

行为：

* `setex` 写入带 TTL 的键；

* `get` 已过期键时返回 `NOT_FOUND`；

* `ttl` 返回剩余有效时间；

* 普通 `set` 写入永久键；

* 删除、覆盖过期键行为保持一致。

运行时存储需保存：
    valueexpires_at

WAL 中保存绝对过期时间，而不是剩余秒数，避免服务器重启后 TTL 被重新计算。

启动恢复 WAL 时：

* 未过期数据正常恢复；

* 已经过期数据不再恢复为有效键。

### Acceptance

至少覆盖：

* TTL 键正常读写；

* TTL 到期后查询失败；

* TTL 键被普通 `set` 覆盖；

* TTL 键删除；

* 服务器重启后剩余过期时间不会重置；

* 已过期记录恢复时不会重新生效。

W-02 WAL Compact
----------------

### 目标

解决 WAL 长期只追加导致文件无限增长和启动恢复成本不断增加的问题。

### Implementation

增加显式 WAL 压缩能力，例如：
    compact

压缩逻辑：
    当前 PersistentStore 状态        ↓生成新的完整 WAL 临时文件        ↓flush        ↓sync_data        ↓确认写入成功        ↓替换旧 WAL

禁止直接先清空原 WAL 再重写。

Compact 后：

* 最终 KV 状态不变；

* 已删除键不再保留无效历史；

* 同一键只保留恢复最终状态所需记录；

* TTL 键保留正确的绝对过期时间。

### Acceptance

至少覆盖：

* 多次覆盖后 WAL 明显缩小；

* delete 的历史记录被消除；

* compact 前后内存状态一致；

* compact 后重启恢复结果一致；

* compact 过程中失败不得破坏原 WAL；

* TTL 数据 compact 后语义保持正确。

W-03 服务器压力测试
------------

### 目标

将“支持多个客户端”从功能验证升级为可量化性能验证，并分析当前架构瓶颈。

### Implementation

新增独立 benchmark / load-test 工具，例如：
    kv-bench --clients 100 --requests 10000

至少统计：
    并发客户端数总请求数成功数失败数总耗时吞吐量 req/sP50 latencyP95 latencyP99 latency

至少测试：
    1 client10 clients50 clients100 clients

可根据本机能力增加更高并发档位。

分别考虑：

* 纯读场景；

* 读写混合场景；

* 高比例写场景。

压测结果需要能够观察现有：
    Arc<Mutex<PersistentStore>>        +WAL flush / sync_data

对写吞吐和尾延迟的影响。

### Acceptance

* 压测工具能够重复执行；

* 不依赖手工操作；

* 统计结果可保存；

* 高并发期间服务器不得 panic；

* 压测完成后数据状态仍然正确；

* 已确认写入的数据重启后可以恢复；

* 输出一份简短性能结果与瓶颈分析。

W-04 轻量 Web Dashboard
---------------------

### 目标

只实现答辩展示必要的服务器可观测页面，不建设复杂 Web 管理系统。

### 页面展示

至少包含：
    Server StatusUptimeActive ClientsCurrent KeysTTL KeysExpired KeysTotal RequestsErrorsGET CountSET CountDELETE CountCurrent ThroughputWAL SizeLast CompactCompact Before / After Size

### 原则

只做轻量展示：

* 不做登录；

* 不做用户系统；

* 不做复杂前端框架；

* 不做完整 KV Web 编辑器；

* 不让 Web 页面直接侵入核心存储逻辑。

优先采用：
    静态 HTML + CSS + 少量 JS        +简单状态接口

Dashboard 应能够在压力测试运行期间实时观察：

* Active Clients；

* Request Count；

* Throughput。

并能在 TTL / Compact 演示时观察：

* TTL Keys / Expired Keys；

* WAL 压缩前后大小。

### Acceptance

现场可完成：

1. 打开 Dashboard；

2. 运行压测，页面指标发生变化；

3. 创建 TTL 键并观察过期；

4. 制造 WAL 历史数据；

5. 执行 compact；

6. 页面显示 WAL 大小明显下降。

集成要求
====

四个扩展必须继续保持现有核心架构：
    CLI / Protocol      ↓TCP Server      ↓Arc<Mutex<PersistentStore>>      ↓BTreeMap + WAL

不得为了 Dashboard 或压测重写核心系统。

所有扩展必须补充对应自动化测试。

完成后重新执行：
    cargo fmt --checkcargo clippy --all-targets --all-features -- -D warningscargo testcargo build

并重新完成：

* 双客户端访问；

* 重启恢复；

* WAL 损坏处理；

* TTL；

* Compact；

* 压力测试；

* Dashboard 答辩演示。

* * *

推荐执行顺序
======

    W-01 TTL  ↓W-02 WAL Compact  ↓W-03 压力测试  ↓W-04 Web Dashboard  ↓最终集成验收

其中前三项先形成真实系统能力，Dashboard 最后只负责展示现有状态和测试结果。
