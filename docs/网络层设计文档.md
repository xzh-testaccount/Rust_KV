# 网络层设计文档

## 1. 概述

本项目网络层基于 **Tokio** 异步运行时，实现了一个支持持久化的键值存储系统的客户端与服务器。网络层负责：

- 解析命令行参数，生成客户端或服务器配置
- 建立 TCP 连接，处理请求/响应的编解码
- 使用自定义的简单文本协议（行协议）进行通信
- 集成持久化存储（WAL）与存储引擎

网络层分为两个独立模块：

- **异步客户端**（`kv-client`）——提供交互式命令行界面，用户可输入命令并显示服务器响应。
- **异步服务器**（`kv-server`）——监听端口，为每个客户端连接生成独立任务，并发处理请求。

------

## 2. 客户端设计

### 2.1 功能概述

- 连接到指定服务器（默认 `127.0.0.1:7878`）
- 提供交互式命令行提示符 `kv>`，支持以下命令：
  - `set KEY VALUE` —— 设置键值对
  - `get KEY` —— 获取键对应的值
  - `delete KEY` —— 删除键
  - `keys` —— 列出所有键
  - `status` —— 获取存储条目数
  - `ping` —— 测试连接
  - `quit` —— 退出客户端
- 解析用户输入，构造协议请求，发送给服务器，并展示响应结果。

### 2.2 核心组件

- **`ClientConfig`**：存储服务器地址，支持 `--server` 和 `--help` 命令行选项。
- **`run(config: ClientConfig)`**：主循环，异步读取 stdin，解析命令，发送请求，接收响应并显示。
- **辅助函数**：
  - `parse_command`（来自 `protocol` 模块）将用户输入转换为 `Request` 枚举。
  - `encode_request_line` 将 `Request` 编码为字节帧。
  - `read_frame_async` 从网络读取一个完整的帧（行）。
  - `parse_response_line` 将响应行解析为 `Response`。
  - `display_response` 根据响应类型格式化输出。

### 2.3 错误处理

- 输入错误（如未知命令、参数缺失）会显示提示信息，不中断循环。
- 网络错误（连接失败、发送/接收失败）会显示错误并退出。
- 服务器返回的错误响应（如键不存在）会显示错误代码和消息。

------

## 3. 服务器设计

### 3.1 功能概述

- 绑定指定地址（默认 `127.0.0.1:7878`）
- 使用 `TcpListener` 接受客户端连接
- 每个连接由独立的 Tokio 任务处理，实现并发
- 支持优雅关闭（通过 Ctrl+C 信号）
- 集成持久化存储（WAL），支持同步/异步刷盘配置

### 3.2 核心组件

- **`ServerConfig`**：包含绑定地址、WAL 路径、同步标志（`sync`）。
- **`run(config: ServerConfig)`**：异步启动监听，创建存储实例（`PersistentStore`），调用 `serve` 主循环。
- **`serve(listener, store)`**：主循环，使用 `tokio::select!` 同时监听新连接和 Ctrl+C 信号。
- **`handle_connection(stream, store)`**：处理单个客户端，循环读取帧，分发请求，写回响应。
- **`dispatch(request, store)`**：根据请求类型，调用存储接口（`set`/`get`/`delete`/`keys`/`len`），构造响应。

### 3.3 并发与同步

- 使用 `Arc<Mutex<PersistentStore>>` 共享存储，保证线程安全。
- 每个客户端任务持有 `store` 的克隆，内部通过异步互斥锁保护存储操作。
- 支持配置 `--sync` 启用同步刷盘。

------

## 4. 协议与帧处理

### 4.1 帧格式

基于简单行协议（Line-based）：

- 请求和响应均以换行符 `\n` 结尾。
- 帧读取器（`read_frame` / `read_frame_async`）返回 `Frame` 枚举：
  - `Line(Vec<u8>)` —— 有效数据行
  - `TooLarge` —— 超过最大长度限制
  - `Incomplete` —— 未收到完整行
  - `Eof` —— 连接关闭

### 4.2 请求编码

- `Request` 枚举（`set`/`get`/`delete`/`keys`/`status`/`ping`/`quit`）通过 `encode_request_line` 序列化为字节串。
- 格式示例：
  - `set key value`
  - `get key`
  - `delete key`
  - `keys`
  - `status`
  - `ping`
  - `quit`

### 4.3 响应编码

- `Response` 包含 `ok` 布尔值、可选的 `error`（错误码+消息）、可选的 `data`（响应数据）。
- `encode_response_line` 将响应序列化为一行，格式如：
  - 成功：`OK data`（数据具体格式由 `ResponseData` 决定）
  - 错误：`ERR code message`
- 解析由 `parse_response_line` 完成。

### 4.4 错误码（`ErrorCode`）

- 常见错误码：`NotFound`、`InvalidRequest`、`FrameTooLarge`、`InvalidUtf8`、`UnknownCommand`、`StorageError` 等。

------

## 5. 请求分发与存储交互

### 5.1 分发流程（服务器端）

1. 收到 `Request` 后，调用 `dispatch`。
2. 根据请求类型：
   - `Ping` → 返回 `Pong`
   - `Quit` → 返回 `Quit` 并标记连接关闭
   - `Set`/`Get`/`Delete`/`Keys`/`Status` → 调用 `store` 对应方法
3. 存储操作结果封装为 `Response`，通过 `write_response` 写回客户端。

### 5.2 存储接口（`PersistentStore`）

- 提供 `set`、`get`、`delete`、`keys`、`len` 方法。
- 内部使用 `HashMap` 和 WAL 实现持久化。
- 支持 `sync` 模式，在每次写操作后强制刷盘。

------

## 6. 配置与命令行解析

### 6.1 客户端配置

- `--server HOST:PORT` —— 指定服务器地址
- `--help` —— 显示帮助信息
- 默认地址 `127.0.0.1:7878`

### 6.2 服务器配置

- `--bind HOST:PORT` —— 监听地址
- `--data PATH` —— WAL 文件路径
- `--sync` —— 启用同步刷盘（默认为异步）
- `-h, --help` —— 显示帮助
- 默认值：`bind=127.0.0.1:7878`、`data=data/kv.wal`、`sync=false`

### 6.3 解析逻辑

- 使用迭代器遍历参数，检查重复选项和缺失值。
- 遇到 `--help` 时，若与其他选项混用则报错。
- 返回 `Ok(Some(config))` 或 `Ok(None)`（仅显示帮助）或 `Err`。

------

## 7. 错误处理

- 使用自定义 `AppError`，包含错误码和可读消息，便于客户端显示和日志记录。
- 网络层将底层 `io::Error`、解析错误等统一转化为 `AppError`。
- 客户端错误输出格式：`[ERROR_CODE] message`。
- 服务器错误响应以协议形式返回给客户端，不中断服务（除非致命错误）。

------

## 8. 并发与异步

- 基于 **Tokio** 运行时，使用 `async/await`。
- 服务器主循环使用 `tokio::select!` 同时处理 accept 和信号。
- 每个客户端连接生成一个独立的 Tokio 任务，实现高并发。
- 存储共享通过 `Arc<Mutex<...>>`，内部使用 `tokio::sync::Mutex` 避免阻塞运行时线程。
- 客户端使用 `tokio::io` 异步读写 stdin/stdout，保证交互流畅。

------

## 9. 持久化集成

- 服务器启动时通过 `PersistentStore::open(wal_path)` 打开或创建 WAL。
- 存储操作（`set`/`delete`）会自动追加 WAL 记录，并在 `sync` 模式下立即刷盘。
- 故障恢复：启动时重放 WAL 重建内存状态（由 `PersistentStore` 内部实现）。
- 客户端不感知持久化细节，所有操作均通过协议交互。

------

## 10. 测试与扩展

### 10.1 单元测试

- 服务器模块包含简单测试，验证默认配置符合预期。
- 协议解析、帧读取、编解码等均有独立测试（位于相应模块）。

### 10.2 扩展性

- 协议基于文本行，易于扩展新命令，只需在 `Request`/`Response` 枚举中添加变体，并在解析/分发中实现对应逻辑。
- 存储层可替换（如改用 RocksDB），只需实现相同接口。
- 服务器支持通过 `--sync` 切换同步/异步，便于性能调优。

------

## 11. 总结

网络层采用整洁的异步架构，分离了协议处理、业务逻辑和持久化，既保证了高并发性能，又提供了友好的命令行交互。清晰的错误处理和配置解析增强了健壮性，为后续功能扩展奠定了良好基础。
